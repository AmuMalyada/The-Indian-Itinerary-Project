# Dataset Understanding

_Generated by `scripts/02_profile.py`. Phase 1 deliverable: understand every
dataset before writing any transformation logic._

## Summary

This project draws on **two unrelated data domains** packaged together on Kaggle:

1. **Real attraction + climate data** (`top_indian_places`, `temperature_data`) —
   factual, usable for genuine travel-planning analytics.
2. **Synthetic user-engagement data** (`sim_destinations`, `sim_reviews`,
   `sim_user_history`, `sim_users`) — generated/mock data, useful for practicing
   recommendation-system and ML workflows, but **not factual** and not the same
   entities as domain 1 (see coverage note below). This project keeps the two
   domains in clearly separated, honestly-labeled tables rather than faking a
   1:1 merge between them.

## Cross-dataset coverage note

- `top_indian_places.City` vs `temperature_data.location`: **64 of 214** unique cities in the attractions table have a matching climate record (exact, case-insensitive name match). The remaining cities keep `NULL` climate fields rather than an invented average — this is documented, not silently dropped.

- `sim_destinations` vs `top_indian_places`: only 1 accidental name collision across 1,000 vs 325 rows, and `sim_destinations` only covers 5 states. The two are **not** joined as if they were the same entity.
